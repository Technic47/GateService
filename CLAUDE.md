# Gate Service — Контекст проекта

## Суть проекта
Единая точка входа (auth gate) для доступа к сервисам, размещённым на домашнем сервере, разворачивается на VPS.

Проблема которую решает: сервисы на домашнем сервере (сейчас — FashionMark) сейчас торчат наружу через reverse SSH-туннель + Nginx с Basic Auth. Basic Auth не даёт: нормальной регистрации, ролей, разграничения доступа по сервисам. Authelia и Tinyauth не подошли — оба жёстко требуют настоящий домен для cookie-сессий (валидация domain c точкой), а домена сейчас нет и заводить его не планируется (см. "Ограничения" ниже). Решение — написать свой минимальный gate.

**Ключевой принцип:** вся проверка авторизации происходит на VPS, до туннеля. Неавторизованный/ботовый трафик не должен долетать до домашнего сервера вообще.

## Текущий статус

**БД-инфраструктура готова:** PostgreSQL 16 в Docker с настроенной streaming replication между двумя серверами (primary/standby, см. раздел "База данных" ниже) — поднята, проверена (`pg_stat_replication` показывает `state = streaming`).

**Сервис развёрнут на primary VPS и работает (15.09.2026).** JVM-образ в Docker, `network_mode: host`. Вход — `https://144.31.187.7`, FashionMark — `https://144.31.187.7:8843` за `auth_request`. Basic Auth в Nginx снят. `mvn clean package` проходит на Java 25 + Spring Boot 4.1.1. Реализовано всё из раздела "Что должен делать gate-service" плюс журнал активности и страница настроек гейта.

Что сделано:
- Сущности, Flyway-миграция `V1__init.sql`, репозитории
- Регистрация/логин (bcrypt), роли ADMIN/USER, блокировка, лок по неудачным попыткам
- `/verify` для Nginx `auth_request`
- Портал выбора сервиса (при единственном доступном сервисе экран пропускается)
- Админка: пользователи, сервисы, журнал активности, настройки гейта
- Docker-сборка (JVM и native), docker-compose с Dozzle

**Запускался и проверен на живой БД** (локальный PostgreSQL 16 в Docker, профиль `dev`): Flyway применяет миграцию, `ddl-auto=validate` проходит, все страницы отдают 200, вход/выход и CSRF работают, `/verify` отвечает 200/401/403 по делу, пользователь с одним сервисом редиректится прямо в него, USER на `/admin/**` получает 403, события пишутся в журнал.

Чего ещё нет:
- Native-образ не собирался (на VPS крутится JVM-вариант)
- Тесты есть только на проверку адресов редиректа (`RedirectTargetsTest`)
- Генератор конфига Nginx не выдаёт `server`-блок для самого гейта (443) — он написан руками, см. "Интеграция с Nginx"

Подробности по сборке, переменным окружения и деплою — в `README.md`.

## Архитектура развёртывания

```
Браузер пользователя
    │  https://144.31.187.7  (гейт: вход, портал, админка)
    │  https://144.31.187.7:8843  (FashionMark)
    ▼
Nginx (VPS)
    │  :443 default_server → http://127.0.0.1:9000 (gate-service)
    │  :8843 auth_request /_gate_verify → http://127.0.0.1:9000/verify
    │        200 → proxy_pass https://127.0.0.1:8080
    │        401 → https://144.31.187.7/login?redirect=...   403 → /denied
    ▼
SSH reverse tunnel (autossh, keepalive)
    │  домашний сервер сам инициирует -R 8080:localhost:443
    ▼
Nginx на домашнем сервере (localhost:443, самоподписанный сертификат)
    │
    ▼
FashionMark (localhost:80) — Windows 11 + Docker Desktop/WSL2
```

- Туннель поднимается на домашнем сервере через Windows Task Scheduler (`SSHTunnelVPS`) + watchdog-задача (`SSHTunnelWatchdog`, проверка каждые 2 мин, перезапускает если процесс `ssh.exe` пропал).
- SSH-пользователь на VPS для туннеля — `tunneluser`, ограничен `command=`, `no-pty` — только port forwarding, шелла нет.
- Домен для этой связки нет и не планируется (см. "Ограничения").

## Что должен делать gate-service

1. **Регистрация / логин** — обычная форма, пароли через bcrypt (Spring Security).
2. **Роли** — `ADMIN` (сам пользователь-владелец) и `USER` с самого начала.
3. **Доступ по сервисам** — многие-ко-многим: какой пользователь к какому сервису допущен. Сейчас единственный сервис — `fashionmark`, но модель должна закладывать расширение (реально новых сервисов пока не планируется — Gorilla крутится на оборудовании заказчика, не на домашнем сервере, — но модель не должна упираться в единственность).
4. **Эндпоинт проверки для Nginx** (`auth_request`) — Nginx на VPS будет слать сюда каждый запрос перед проксированием; сервис смотрит cookie/сессию и заголовок с именем запрашиваемого сервиса, отвечает 200 (пропустить) или 401/403 (отказать).
5. **Админка** — простые Thymeleaf-страницы для владельца: список пользователей, выдача/отзыв доступа к сервисам.
6. **Портал выбора сервиса** — после входа. Если пользователю доступен ровно один сервис, экран пропускается и его сразу ведёт в сервис. Админа не перебрасывает: сервис сейчас один, и на редиректе он никогда не увидел бы навигацию в админку. Принудительно показать список — `/portal?choose=1`.
7. **Журнал активности** — входы, отказы, действия админов; фильтры по пользователю, типу, сервису, датам. Срок хранения настраивается, чистка по расписанию.
8. **Страница настройки гейта** — политика регистрации, защита входа, сессии, режим обслуживания, состояние PostgreSQL с репликацией, генератор конфига Nginx.

  - Проверить новый патч: `mvn versions:display-parent-updates -DallowMinorUpdates=false -DallowMajorUpdates=false`

- **Hibernate ORM 7.4.5**, **Flyway 12.4.0**, **PostgreSQL JDBC 42.7.13**

⚠️ **В Spring Boot 4 автоконфигурации разнесены по отдельным модулям** (`spring-boot-flyway`, `spring-boot-thymeleaf`, `spring-boot-security`, ...). Голая библиотека на classpath больше **не** включает автоконфигурацию сама по себе. На этом уже споткнулись: зависимость `org.flywaydb:flyway-core` вместо `spring-boot-starter-flyway` означала, что `FlywayAutoConfiguration` не подхватилась, миграции **молча не выполнялись**, и приложение падало позже и невнятно — на `ddl-auto=validate` с `missing table [activity_log]`. Правило: подключать технологию **через её `spring-boot-starter-*`**, а не напрямую.

⚠️ **Диалект Hibernate задан явно** (`hibernate.dialect: org.hibernate.dialect.PostgreSQLDialect`). Автоопределение открывает соединение и читает метаданные JDBC, поэтому при недоступной БД падает с `Unable to determine Dialect without JDBC metadata` — формулировкой, которая уводит от настоящей причины (соединение вообще не установилось). С явным диалектом наверх всплывает нормальная ошибка подключения. Не убирать.
- **Thymeleaf 3.1.5** — весь UI (логин, регистрация, админка). Без SPA/React — не нужен для форм такого масштаба.
  - ⚠️ **Не использовать `thymeleaf-layout-dialect`** — тянет Groovy, несовместим с GraalVM native-image. Для переиспользуемого layout использовать штатные механизмы Thymeleaf (`th:fragment`, `th:replace`, `th:insert`) без сторонней библиотеки. Так и сделано: `templates/layout.html` отдаёт фрагменты `head(title)`, `topbar`, `flash`.
  - ⚠️ **Не подключать `thymeleaf-extras-springsecurity`.** Отдельный артефакт со своей привязкой к версии Spring Security, а нужны из него ровно два значения. Вместо него `GlobalModelAdvice` кладёт в модель `currentUsername` / `currentIsAdmin`.
  - Артефакт называется `thymeleaf-spring6` даже под Spring Framework 7 — это нормально, не искать несуществующий `thymeleaf-spring7`.
  - Instant в шаблонах форматируется бином `@fmt` (`Formatter`), а не через `#temporals`: у Instant нет зоны, и формат с датой на нём падает с `UnsupportedTemporalTypeException`.
- **PostgreSQL 16** (не SQLite — решение поменяли, см. "База данных" ниже). Нагрузка для самого сервиса тривиальна (несколько таблиц, десяток пользователей); Postgres выбран не по необходимости, а осознанно ради опыта репликации.
- **GraalVM Native Image** — финальная сборка для деплоя. Ориентир по официальным бенчмаркам (Paketo) — ~90 МБ RAM, старт ~0.1 сек для типового Spring Boot native-образа. **Пока не собирался ни разу.**
  - Разрабатывать и отлаживать в обычном JVM-режиме (быстрые итерации), собирать native только на финальном этапе перед деплоем.
  - Профиль `native` объявлен в `pom.xml` явно (`native-maven-plugin`), а не в расчёте на профиль из `spring-boot-starter-parent`.
  - `native-image` уже входит в установленный `~/.jdks/graalvm-jdk-25` — Docker для сборки не обязателен.
  - ⚠️ **На Windows локальная сборка требует MSVC**: Visual Studio Build Tools с нагрузкой *Desktop development with C++*, запуск из «x64 Native Tools Command Prompt». Без этого падает на линковке. Альтернатива без возни — `Dockerfile.native` (образ `ghcr.io/graalvm/native-image-community:25`, тег проверен).
  - Собирать на рабочей машине, **не на VPS**: нужно 8+ ГБ RAM.
  - Проверить совместимость связки Security + JPA + PostgreSQL JDBC-драйвер под native image перед деплоем — возможны edge-cases с reflection/прокси, невидимые в обычной JVM. Первое место, где искать проблемы, — обращения к бинам из шаблонов (`${@fmt.dateTime(...)}`): это SpEL-рефлексия.

## База данных — PostgreSQL streaming replication (уже настроено)

Решение сменили с SQLite на **PostgreSQL с полноценной streaming replication**, осознанно принимая больший расход ресурсов — ради практического опыта репликации, задела на будущие проекты и пункта в резюме. Развёрнуто через Docker (не нативная установка) — на обоих серверах уже поднято и проверено.

**Primary** — `144.31.187.7`, контейнер `pg-primary` (`~/postgres-primary/docker-compose.yml`):
- `wal_level=replica`, `max_wal_senders=3`, `max_replication_slots=3`
- `pg_hba.conf` разрешает `replication` только с IP `2.26.60.167`
- Роль `replicator` с правом `REPLICATION LOGIN`
- Порт `5432` открыт наружу только для IP запасного сервера

**Standby** — `2.26.60.167`, контейнер `pg-standby` (`~/postgres-standby/docker-compose.yml`):
- Данные клонированы через `pg_basebackup -h 144.31.187.7 -U replicator -D ... -P -R -X stream` (флаг `-R` сам создал `standby.signal` и `primary_conninfo`)
- Использует **внешний** Docker volume `pgdata_standby` (`external: true` в compose) — том создавался и наполнялся `pg_basebackup` отдельно, до первого `docker compose up`, поэтому entrypoint-скрипт официального образа не пытается заново инициализировать пустую БД
- Подтверждено рабочим: на primary `SELECT * FROM pg_stat_replication;` показывает строку с `state = streaming`, `client_addr = 2.26.60.167`

**Доступ гейта к БД.** База `gate` и роль `gate` созданы. Postgres читает **не** `pg_hba.conf` из каталога данных образа (там лежит дефолтный, с `host all all all scram-sha-256`), а отдельный файл — путь смотреть через `SHOW hba_file;`. Если он смонтирован одиночным файлом, править через `>>` или `nano`, но не `sed -i`/`vim`: они подменяют inode, и контейнер продолжает видеть старое содержимое. Применять — `SELECT pg_reload_conf();`, проверять — `SELECT * FROM pg_hba_file_rules;`.

Гейт в host-сети приходит в Postgres с адресом самого VPS, отсюда строка `host gate gate 144.31.187.7/32 scram-sha-256`. Раньше, из bridge, он приходил из `172.16.0.0/12`, и там стояло **`trust`** — любой контейнер на VPS мог войти любым пользователем, включая `postgres`, без пароля, а пароль гейта фактически никогда не проверялся. Исправлено: проверено 16.09.2026 — `SELECT * FROM pg_hba_file_rules WHERE auth_method = 'trust' AND type <> 'local'` возвращает 0 строк. `trust` остался только у `local` (сокет внутри контейнера) — это нормально, до него добирается только тот, у кого уже есть `docker exec`.

**Важно для приложения:** Spring Boot подключается к **primary** (`144.31.187.7:5432`) как к обычному Postgres. Standby существует для disaster recovery/будущего failover, не для read-балансировки — читающих запросов на него не направлять, если явно не настроено отдельно.

⚠️ **С домашней машины к primary не подключиться, и это правильно.** TCP-порт 5432 отвечает, но `pg_hba.conf` содержит правило только для standby (`2.26.60.167`) и только для репликации, поэтому соединение умирает на аутентификации:

```
FATAL: no pg_hba.conf entry for host "109.252.91.146", user "gate", database "gate"
```

Чинить это добавлением домашнего IP в `pg_hba.conf` **не надо**: адрес динамический, править пришлось бы постоянно, а заодно это открыло бы аутентификацию Postgres в интернет. Для разработки есть локальная база — `docker-compose.dev.yml` (Postgres 16, та же мажорная версия). Если нужен именно живой primary — SSH-туннель, без правки серверного конфига:

```bash
ssh -L 5433:localhost:5432 user@144.31.187.7
GATE_DB_HOST=localhost GATE_DB_PORT=5433 mvn spring-boot:run -Dspring-boot.run.profiles=dev
```

**Не сделано, но стоит сделать перед продакшн-использованием:**
- SSL для соединения репликации (трафик сейчас идёт по публичному интернету между двумя разными хостерами без TLS — риск). **Начато обсуждение 16.09.2026, ничего не менялось.** Порядок, о котором договорились:
  1. сертификат + `ssl = on` на primary, `pg_hba` пока не трогать (смена `ssl` применяется `pg_reload_conf()`, без рестарта);
  2. переподключить standby — дефолтный `sslmode=prefer` сам возьмёт SSL; проверить `pg_stat_replication JOIN pg_stat_ssl USING (pid)` → `ssl = t`;
  3. на standby `sslmode=verify-ca` в `primary_conninfo` и корневой сертификат (`prefer` молча откатывается на открытое соединение);
  4. только потом `host` → `hostssl` для строки `replication replicator 2.26.60.167/32`.
  
  ⚠️ `hostssl` при выключенном `ssl` не совпадает ни с чем: текущее соединение живёт, но после любого переподключения standby не войдёт. Со слотом репликации primary будет копить WAL до заполнения диска — Postgres встанет, а с ним и гейт. Перед началом проверить `SHOW ssl;`, `SHOW synchronous_standby_names;` (при синхронной репликации записи гейта повиснут сразу), `SELECT * FROM pg_replication_slots;`.
  
  ⚠️ `pg_hba.conf` в `~/postgres-primary` смонтирован в контейнер одиночным файлом — **не `sed -i`**: он подменяет файл, контейнер продолжит читать старый, а изменение всплывёт неожиданно при следующем рестарте. Писать через `sed ... > /tmp/new && cat /tmp/new > pg_hba.conf` или `nano`, пробелы в шаблоне — `\s+`. Гейт эта правка не затрагивает: его строка `host gate gate 144.31.187.7/32` отдельная.
- Реальный тест failover: `pg_promote()` на standby, проверка что приложение может переключиться на бывший standby как на новый primary

**Отдельная, отложенная идея:** попробовать ту же репликацию через Kubernetes (k3s, не полный kubeadm) как отдельное учебное упражнение — сознательно решили не смешивать с этим проектом, делать после того как rate-service и Docker-репликация полностью доведены до конца.

## Модель данных (реализовано)

Схема создаётся Flyway (`src/main/resources/db/migration/V1__init.sql`), `ddl-auto=validate` — расхождение сущностей и миграции ловится на старте.

```java
User                      // таблица users
  - id, username (unique, регистронезависимо), passwordHash (bcrypt)
  - Role role             // ADMIN | USER
  - blocked               // ручная блокировка админом
  - approved              // false для регистрации в режиме APPROVAL
  - createdAt, lastLoginAt
  - failedAttempts, lockedUntil   // лок после серии неудачных попыток, хранится в БД
  - Set<ProtectedService> services // ManyToMany через user_service_access

ProtectedService          // таблица services
  - id, name (unique), displayName, description, icon, sortOrder, enabled
  - scheme, host, port    // UPSTREAM: куда проксирует Nginx после разрешения
  - publicUrl             // КУДА ВЕСТИ БРАУЗЕР после логина

ActivityLog               // таблица activity_log
  - id, occurred_at, username (строкой!), userId, type, category
  - success, serviceName, ip, userAgent, detail

GateSetting               // таблица gate_settings, плоский key/value
  - settingKey, settingValue
```

Решения, которые легко нечаянно сломать:

- **Класс называется `ProtectedService`, а не `Service`** — иначе конфликт с `org.springframework.stereotype.Service`.
- **`host`/`port` и `publicUrl` — про разное.** `host:port` это upstream с точки зрения VPS (`127.0.0.1:8080`, локальный конец SSH-туннеля) — используется для конфига Nginx и проверки доступности порта. `publicUrl` (`https://144.31.187.7:8843`) — то, куда гейт отправляет браузер. До upstream браузер не достучится: `127.0.0.1` на VPS это сам VPS. Если `publicUrl` пуст, гейт подставит upstream и переход из портала не сработает.
- **У `ProtectedService` переопределены `equals`/`hashCode` по id**, `hashCode` — константа по классу. Без этого `Set.contains()` сравнивал бы экземпляры из разных запросов по ссылке, и в админке не проставлялись бы галочки выданных доступов.
- **`activity_log.username` — строка без FK на users.** Журнал должен пережить удаление пользователя и фиксировать попытки входа под несуществующим логином. `user_id` — подсказка для ссылок, может указывать в никуда.
- **Колонки `occurred_at`, `setting_key`, `setting_value`** названы так, чтобы не спорить с ключевыми словами SQL (`at`, `key`, `value`).
- **Уникальность username/name — через `CREATE UNIQUE INDEX ... (lower(...))`**, а не `UNIQUE(...)`: обычный constraint пропустил бы пару `Admin`/`admin`.
- **`open-in-view: false`.** Ленивые коллекции догружаются явно через `@EntityGraph` — не убирать его из методов репозитория, иначе шаблоны упадут на `LazyInitializationException`.

## Эндпоинты (реализовано)

```
GET/POST  /login                     форма входа + регистрации (две вкладки)
POST      /register
GET       /logout                    подтверждение выхода — открывается ссылкой (закладка, кнопка
                                     «Выйти», которую Nginx встраивает в страницы сервиса)
POST      /logout                    сам выход (LogoutFilter, с CSRF)
GET       /denied                    "доступа нет", сюда Nginx уводит при 403

ANY       /verify                    <- Nginx auth_request
                                     читает cookie сессии + заголовок X-Service-Name,
                                     отвечает 200 / 401 / 403.
                                     При 200 отдаёт X-Gate-User и X-Gate-Role —
                                     их можно пробросить в сервис через auth_request_set,
                                     и X-Gate-Assertion (подписанный токен Gate Auth), если задан ключ

GET       /  , /portal               выбор сервиса; при единственном доступном сервисе
                                     редирект прямо в него. /portal?choose=1 — показать список
GET       /go/{name}                 переход в сервис (нужен, чтобы записать это в журнал)

GET       /admin/users               список пользователей
GET/POST  /admin/users/new           создание
GET/POST  /admin/users/{id}          карточка / сохранение
POST      /admin/users/{id}/access   быстрая выдача-отзыв доступов прямо из списка
POST      /admin/users/{id}/block    блокировка / разблокировка
POST      /admin/users/{id}/password сброс пароля
POST      /admin/users/{id}/delete

GET       /admin/services            список (?probe=1 — TCP-проверка портов)
GET/POST  /admin/services/new
GET/POST  /admin/services/{id}
POST      /admin/services/{id}/delete

GET       /admin/activity            журнал с фильтрами и постраничной навигацией

GET/POST  /admin/setup               настройки гейта, состояние, генератор конфига Nginx
POST      /admin/setup/purge-activity

GET       /.well-known/jwks.json     Gate Auth: публичный ключ подписи, без аутентификации
GET       /auth/handoff              Gate Auth, вход из LAN (direct mode): ответ формой POST на callback

GET       /actuator/health           без аутентификации; остальной actuator — только ADMIN
```

Важное про `/verify`:

- **Ходит в БД на каждый запрос**, а не берёт доступы из сессии. Осознанный размен: отзыв доступа и блокировка действуют мгновенно, а не после перелогина. При десятке пользователей и запросе по уникальному индексу нагрузка пренебрежима — но если сервисов станет заметно больше, смотреть надо сюда.
- **Разрешённые проверки по умолчанию в журнал не пишутся.** Nginx дёргает `/verify` на каждый запрос, включая статику; журнал заполнился бы за минуты. Включается галочкой в настройках на время разбора конкретной проблемы. Отказы пишутся всегда.
- **ADMIN по умолчанию проходит во все сервисы** (настройка `adminBypassesAccess`), иначе пришлось бы выдавать доступ самому себе в каждый новый сервис.
- **Имя сервиса не передано — отказ.** Почти всегда это значит, что в Nginx забыли `proxy_set_header X-Service-Name`. Гейт отвечает 403 с явной причиной, а не пропускает запрос.

## Gate Auth — общий стандарт авторизации приложений (ветка `common_auth`)

Гейт выдаёт приложениям подписанные токены по стандарту **Gate Auth v1**. Спецификация и библиотека —
в соседнем проекте `../gate-auth` (`docs/gate-auth-spec-v1.md` — нормативная). Гейт использует только
`gate-auth-core` (подпись Ed25519, без зависимостей); приложения — `gate-auth-spring-boot-starter`.

Что добавлено:
- **`/verify` → `X-Gate-Assertion`** (edge mode): JWT на 60 с для `aud = X-Service-Name`, с `sub` = id
  пользователя, ролью гейта, ролью в приложении и списком доступных сервисов. Кешируется на (сессия, сервис),
  пока токену осталось ≥ 30 с; сброс кеша — при правке пользователя в админке. `X-Gate-User`/`X-Gate-Role`
  остались для сервисов без библиотеки.
- **`GET /.well-known/jwks.json`** — публичный ключ, без аутентификации.
- **`GET /auth/handoff`** (direct mode, вход из LAN): проверяет запрос и **точное** совпадение `redirect_uri`
  с зарегистрированным, при необходимости ведёт на форму входа и возвращается, отвечает автоотправляемой формой
  POST (`id_token` или `error=login_required|access_denied`, плюс `state`). На незарегистрированный адрес
  не уходит ничего — только страница ошибки гейта. CSP разрешает ровно один скрипт (по хешу) и отправку формы
  только на origin приложения. В журнале — `HANDOFF_ISSUED` / `HANDOFF_DENIED`.
- **Роль в приложении** — таблица `user_service_role` (V2). Не колонкой в `user_service_access`: та таблица —
  `@ManyToMany`, Hibernate вправе пересоздать её строки и потерять лишнюю колонку. Роль живёт, только пока выдан
  доступ. В форме пользователя — поле справа от галочки сервиса; быстрые галочки в списке роли не трогают.
- **Сервис**: «Путь API» (`api_prefix`), «Вход из LAN» (`direct_enabled`), «Адреса возврата» (`redirect_uris`,
  по одному на строку, только https, кроме localhost).
- **Генератор Nginx**: в оба `location` — `auth_request_set $gate_assertion …` + `proxy_set_header X-Gate-Assertion`;
  для пути API — отдельный `location` с `error_page 401/403` → JSON (`application/problem+json`, `login_url`),
  а не редирект: `fetch` из SPA не может идти по редиректу на HTML-форму.

Ключ подписи: `GATE_SIGNING_KEY` — приватный JWK одной строкой (едет из локального `.env`, как остальные
секреты) или `GATE_SIGNING_KEY_FILE`. Сгенерировать: `KeyTool` из `gate-auth-core` (см. `.env.example`).
**Без ключа гейт работает как раньше** — без токенов и без `/auth/handoff`. Ключ задан, но не читается —
гейт не стартует (молчаливый запуск без подписи сломал бы вход во все приложения).

⚠️ `gate-auth-core` пока не в Maven Central:
- локально: сначала `mvn install` в `../gate-auth`;
- Docker: `Dockerfile` собирает его из дополнительного контекста `gateauth` (`../gate-auth`), он прописан в обоих
  compose-файлах. Голый `docker build` — с `--build-context gateauth=../gate-auth`. При деплое через
  `docker context vps-germany` каталог `../gate-auth` тоже уезжает с рабочей машины.
  После публикации в Central этот блок из Dockerfile-ов убрать.

Тесты: `GateAuthIntegrationTest` поднимает **PostgreSQL 16 через Testcontainers** — для `mvn test` нужен
локальный Docker. Контейнер стартует в текущем docker context: перед тестами проверить, что это
`desktop-linux`, а не `vps-germany`.

Порядок выката:
1. `mvn install` в `../gate-auth`; сгенерировать ключ, положить приватный JWK в `GATE_SIGNING_KEY` в `.env`.
2. Деплой гейта (миграция V2 применится сама). Старые сервисы ничего не заметят.
3. Для приложения на gate-auth: завести сервис (путь API, при необходимости — вход из LAN и адрес возврата),
   выдать доступ и роли, перегенерировать блок Nginx на странице настроек, `nginx -t && systemctl reload nginx`.
4. В приложение — публичный ключ (PEM из KeyTool) в `gate.auth.public-keys`.

```
├── service/   AccessVerifier (решение о доступе), ActivityService + ActivityWriter (журнал),
│              UserAdminService, ServiceCatalogService, GateSettingsService,
│              HealthProbe, NginxConfigGenerator, DatabaseStatusService
├── web/       AuthController, PortalController, VerifyController, GlobalModelAdvice, Formatter
│              └── admin/  AdminUsersController, AdminServicesController,
│                          AdminActivityController, AdminSetupController
└── config/    DataSeeder, ActivityRetentionJob
```

Пара мест, где решение неочевидно и его легко «починить» обратно:

- **`ActivityWriter` — отдельный бин, а не метод `ActivityService`.** Запись журнала идёт в `REQUIRES_NEW`, чтобы упавшая вставка не пометила транзакцию вызывающего кода как rollback-only и не откатила, скажем, саму регистрацию. `REQUIRES_NEW` работает только через прокси, а вызов своего же метода изнутри бина прокси минует — поэтому и отдельный класс.
- **Настройки гейта кешируются в памяти** (`GateSettingsService` держит иммутабельный снимок): они читаются на каждом `/verify`. Цена — при нескольких экземплярах сервиса они разъедутся. Гейт разворачивается в одном.
- **Последний ADMIN неприкосновенен** — `UserAdminService` не даёт его удалить, заблокировать или понизить до USER. Без этого легко получить систему, в админку которой никто не войдёт, и чинить это пришлось бы руками в psql.
- **Открытые редиректы.** Параметр `redirect` в форме логина приходит снаружи, поэтому принимается только относительный путь внутри гейта или адрес внутри публичного URL зарегистрированного сервиса. Проверка — в `security/RedirectTargets`: адрес разбирается `java.net.URI`, схема/хост/порт/путь сравниваются по отдельности, адрес с userinfo отвергается. **Не возвращать сравнение строками** (`startsWith(publicUrl)`): так было, и `https://144.31.187.7:8843@evil.com/` его проходил — браузер считает всё до `@` логином и уходит на evil.com сразу после ввода пароля на настоящем гейте. Там же отсекаются `//host`, `/\host` и управляющие символы: браузеры превращают их в чужой хост. Набор обходов — в `RedirectTargetsTest`.
- **Выход: `GET /logout` — страница подтверждения, `POST /logout` — сам выход.** Пользователь с одним сервисом после входа сразу попадает в сервис и шапки гейта с кнопкой «Выйти» не видит, а сам сервис про гейт не знает. Поэтому Nginx встраивает в HTML-страницы сервиса ссылку на `https://144.31.187.7/logout` (`sub_filter`, генерирует `NginxConfigGenerator.appendLogoutButton`). Именно ссылка, а не форма: сервис на другом порту — другой origin, POST оттуда ушёл бы без CSRF-токена гейта. **Не делать выход по GET без подтверждения**: тогда любая чужая страница разлогинивала бы пользователя картинкой с `src=/logout`. Выход закрывает сразу все сервисы — сессия одна на всех.
- **`deleteCookies` берёт имя из `server.servlet.session.cookie.name`** (`GATESESSION`). Раньше там был захардкожен `JSESSIONID`, и cookie сессии при выходе не удалялась (сама сессия при этом инвалидировалась).

## Логирование и Dozzle

Каждое событие пишется **в два места**:

1. **Таблица `activity_log`** — источник для `/admin/activity` с фильтрами и историей.
2. **Логгер `gate.activity`** — одна строка в stdout:
   `LOGIN_FAILURE user=petya service=- ip=203.0.113.9 ok=false Неверный логин или пароль`

Dozzle (`amir20/dozzle`) поднимается тем же `docker-compose.yml` на `127.0.0.1:9001`. Он показывает **stdout контейнеров**, а не действия пользователей: срез по пользователям и отказам даёт только `/admin/activity`. Польза Dozzle в другом — видно логи Postgres, Nginx и самого гейта, включая то, что случилось до того, как запись в БД вообще стала возможна.

Собственная авторизация Dozzle намеренно выключена: его следует завести сервисом `dozzle` с upstream `127.0.0.1:9001` на странице `/admin/services` и закрыть той же авторизацией, что и всё остальное. Заодно это наглядная проверка, что гейт работает.

## Первичное наполнение

`DataSeeder` при пустой базе создаёт администратора и сервис `fashionmark`. Пароль админа берётся из `GATE_ADMIN_PASSWORD`; если переменная не задана — генерируется случайный и **один раз** печатается в лог, чтобы гейт не поднялся с предсказуемым паролем. Повторный старт ничего не перезаписывает.

`GATE_REMEMBER_ME_KEY` обязателен и должен быть постоянным: случайный ключ при каждом старте разлогинит всех, а общеизвестный позволит подделать токен.

## Интеграция с Nginx на VPS (сделано 15.09.2026)

Nginx стоит на хосте (не в Docker). Файлы в `/etc/nginx/sites-enabled/`:

| Файл | Порт | Что делает |
|---|---|---|
| `default` | 80 | `return 301 https://...` — по http гейт не работает, cookie `Secure` |
| `default` | 443 `default_server` | `proxy_pass http://127.0.0.1:9000` — сам гейт |
| `home-access` | 8843 | FashionMark: `auth_request` к гейту, `proxy_pass https://127.0.0.1:8080`, `sub_filter` с кнопкой «Выйти» |
| `vpn` | 443 (SNI `vpn.kuz-net-dom.ru`), 80 | чужое, не трогать; на любой путь отвечает `OK` |
| `xui-panel` | 8844 | панель 3x-ui, не трогать |

`auth_basic` удалён, резервные копии старых файлов — в `/root/*.bak`.

**Блоки сервисов руками не писать.** Страница `/admin/setup` генерирует готовый блок под текущий список сервисов, с уже подставленными именами в `X-Service-Name`. Имя в заголовке обязано побайтово совпадать с `services.name` в БД, и это ровно то место, где заводится опечатка, которую потом долго ищут. Блок для самого гейта (443) генератор не выдаёт — он в `README.md`, раздел "Nginx".

На что наступили при переключении — не повторять:

- **Гейт на 443 обязан быть `default_server`.** По голому IP браузер не шлёт SNI, и Nginx отдаёт запрос серверу по умолчанию. Без этого им был `vpn`, и вместо формы входа показывалось `OK`.
- **Upstream сервиса в гейте — туннель `127.0.0.1:8080`**, не старый `:8843` и не `172.20.0.1:...`. Гейт трафик не проксирует: upstream нужен проверке доступности и генератору. Зелёный статус при upstream на старый basic-auth Nginx ничего не значит.
- **`publicUrl` сервиса пуст → браузер уходит на `https://127.0.0.1:8080`** и получает `ERR_CONNECTION_REFUSED` на своей же машине. Статус при этом зелёный.
- **`location /` в `home-access` проксирует в туннель, не в гейт.** Когда туда попал `proxy_pass http://127.0.0.1:9000`, на `:8843` открылся второй портал, и «переход в сервис» бесконечно возвращал на него же.
- **Файлы конфига перезаписывать целиком** (`tee <<'EOF'`), а не править поверх: закомментированный `# listen 443 ssl default_server;` рядом с раскомментированным IPv6-вариантом отдавал гейт только по IPv6, и `nginx -t` это не ловит.
- **Кнопка «Выйти» — три строки в `location /` сервиса** (не в `/_gate_verify` и не в `@gate_login`/`@gate_denied`: те страниц сервиса не отдают). `proxy_set_header Accept-Encoding "";` обязателен: со сжатым ответом upstream-а `sub_filter` молча ничего не делает. Нужен модуль `http_sub_module` — в штатном пакете Ubuntu есть (`nginx -V 2>&1 | grep -o with-http_sub_module`). Не видно кнопку — искать `logout` в исходнике страницы (`Ctrl+U`): нет — строки не в том `location` или Nginx не перезагружен; есть — её перекрывают стили сервиса, править `right`/`bottom` в `style`.
- **`server.forward-headers-strategy: native`** в `application.yml`. Nginx ходит в гейт по http, и без этого Spring строит абсолютные редиректы на `http://...`. Доверяет `X-Forwarded-*` только от внутренних адресов — гейт в host-сети, Nginx приходит с `127.0.0.1`.

Блок сервиса с `auth_request` (сокращённо; полный вариант — из генератора):
```nginx
location = /_gate_verify {
    internal;
    proxy_pass http://127.0.0.1:9000/verify;
    proxy_pass_request_body off;
    proxy_set_header Content-Length "";
    proxy_set_header X-Service-Name "fashionmark";
    proxy_set_header X-Original-URI $request_uri;
}

location / {
    auth_request /_gate_verify;
    error_page 401 = @gate_login;    # не вошёл → на форму входа
    error_page 403 = @gate_denied;   # вошёл, но доступа нет → на страницу отказа
    proxy_pass https://127.0.0.1:8080;

    # кнопка «Выйти» поверх страниц сервиса
    proxy_set_header Accept-Encoding "";
    sub_filter_once on;
    sub_filter '</body>' '<a href="https://144.31.187.7/logout" style="position:fixed;...">Выйти</a></body>';
}
```

⚠️ **401 и 403 обязаны вести в разные места.** Если оба уводят на логин, пользователь без доступа попадёт в бесконечный редирект: он уже аутентифицирован, логин отправляет его обратно в сервис, сервис снова отвечает 403.

**Порты:** `9000` — гейт, `9001` — Dozzle. Оба **только на `127.0.0.1`**, наружу не открываются: доверие к заголовку `X-Forwarded-For` держится ровно на том, что снаружи до этих портов не достучаться. Перед деплоем всё равно проверить `ss -tulnp`.

**Гейт в `network_mode: host`, а не в bridge.** Туннель слушает `127.0.0.1:8080` на хосте, а из bridge-контейнера `127.0.0.1` — это сам контейнер: проверка доступности сервиса всегда показывала «недоступен». В host-сети секция `ports` не действует, поэтому гейт сам слушает `127.0.0.1` (`GATE_BIND_ADDRESS`). Dozzle остался в bridge.

Занято на primary: 43615/48157 (AmneziaWG x2), 8443 (Hysteria2), 8080 (SSH-туннель, только loopback), 3000/3001 (AdGuard/Tinyauth), 5432 (pg-primary), 80/443/8843/8844 (Nginx, см. таблицу выше).

**ufw:** 8843 открыт наружу — это безопасно, пока в `home-access` стоит `auth_request`. Правила `8843 ALLOW 127.0.0.1` и `8843 ALLOW 172.16.0.0/12` лишние (перекрыты `ALLOW Anywhere`). Порт 8080 в ufw не нужен: туннель на loopback, а сам он приходит исходящим соединением на 22.

**Cookie и порты.** Схема работает без домена потому, что cookie не различают порты: сессия, выставленная гейтом на `144.31.187.7`, уезжает и на `144.31.187.7:8843`. Обратная сторона — cookie обязана быть `Secure`, то есть и гейт, и сервисы только за HTTPS. `GATE_COOKIE_SECURE=false` существует исключительно для локальной отладки.

Поэтому `.env` на VPS нет и не должно быть — секреты меняются в локальном `.env` и применяются `docker compose up -d --force-recreate gate`. Метка контейнера `com.docker.compose.project.working_dir` показывает Windows-путь — это нормально. Для этого проекта используются два контекста: `vps-germany` — прод, `desktop-linux` — локальный Docker Desktop. ⚠️ Перед `docker compose` проверять `docker context ls`: при контексте `desktop-linux` та же команда поднимет гейт локально, а не на VPS (и наоборот). Остальные контексты в списке к проекту не относятся.
- **На primary работают** контейнеры `gate-service` (порт 9000, `network_mode: host`) и `dozzle` (порт 9001), оба только на `127.0.0.1`. В JVM-режиме гейт стоит ~200-300 МБ RAM из доступных 2 ГБ — на первое время терпимо, но это и есть причина довести native-сборку до конца (ориентир ~90 МБ). В `Dockerfile` для JVM-варианта выставлены `-XX:MaxRAMPercentage=60 -XX:+UseSerialGC` — на 1 vCPU параллельный GC только мешает.

## Ограничения
- **Домен принципиально не заводим** — решено не продлевать/использовать `.ru`-домен из-за требования идентификации через Госуслуги для `.ru`-зоны с сентября 2026; альтернативные бесплатные варианты (eu.org) зависают на модерации неделями. Все URL — по голому IP.
- Именно поэтому Authelia/Tinyauth отпали — оба валидируют домен для cookie и по IP не заводятся. Свой сервис такого ограничения не имеет — cookie на голый IP работает нормально в браузерах, ограничение было специфично для тех инструментов (заточены под multi-domain SSO).
